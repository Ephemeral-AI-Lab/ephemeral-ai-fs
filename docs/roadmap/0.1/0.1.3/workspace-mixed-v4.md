## Scope

Replace the high-tier (`100` / `500`) shared Workspace tree used outside `init_namespace`
with profile `workspace-mixed-v4`. Tiers still mean **payload or dirty work**, not inode count.
File count is a capped namespace size. Tiers 1/10 stay `-compact-v2` and keep their compact file lists.

Do not put a 100 MiB large file at tier 100: it cannot coexist with 2,000 other files inside a 100 MiB budget.
Do not raise the 1 GiB logical cap. Do not raise the 2 GiB container.

## Identity, paths, and assignment

Fixture profile: `workspace-mixed-v4`. Domain-separate generated bytes on profile + seed + path + ordinal through the existing bounded generator.

Assignment order, same as mixed-v3: large files first, then small, then medium, by `(shard, file ordinal)` ascending. File ordinal `0..count-1` maps to shard `ordinal / 200` and in-shard file `ordinal % 200`.

Path shape reuses the wide/regular/spine layout of `workspace-shards-v1`, with 200 files per shard:

```text
j < 64:       wide/s{s:03}-f{j:03}.dat
64 <= j <199: regular/s{s:03}/f{j:03}.dat
j == 199:     spine/d001/d002/.../d128/s{s:03}.dat
```

Tier 100 uses 10 shards (2,000 files). Tier 500 uses 25 shards (5,000 files). Wide-directory fan-out is 640 entries at tier 100 and 1,600 at tier 500: a few hundred to low thousands, well under the 32,000-entry readdir-proxy failure. Prepare an empty `dest/` directory.

Frozen metadata remains file mode `0640`, directory mode `0750`, mtime `1700000000.0`.

Seeds remain 1..3. Do not require tier 100 to be a byte-identical prefix of tier 500.

## Peak-bytes rule

Declare parent logical bytes plus expected dirty spool at registration. Reject cases that cannot fit the 2 GiB / no-swap container. Do not raise the container to paper over 100k files.

| Case | Parent logical | Expected dirty spool | Combined | Allowed |
| --- | ---: | ---: | ---: | --- |
| dense-rewrite-100-mixed-v4 | 100 MiB | 100 MiB | 200 MiB | yes |
| dense-rewrite-500-mixed-v4 | 500 MiB | 500 MiB | 1,000 MiB | yes |
| other Wave 1 mixed-v4 rows | 100 or 500 MiB | ≤ 500 × 4 KiB | ≪ 2 GiB | yes |

Dense-500 is 500 MiB tree + 500 MiB rewrite spool; that is allowed. 500 MiB tiny parent + 500 MiB rewrite + 100k inodes is the old failure; do not recreate it.

The 1 GiB **logical** workload cap is unchanged. In-place rewrite does not double logical file bytes.

## Sampled proofs

Every large file gets three 64 KiB ranges (begin, midpoint, end), plus declared small/medium paths, plus topology (`dest/`, `wide/`). Do not read every large-file byte in the proof iteration. Report omissions. Proof ceiling stays 45 s work / 59 s hard. Do not rerun large-tier exhaustive walks at 300 s.

## Git exception (Wave 3; do not block Wave 1)

Git complete-repository cap remains 256 MiB including `.git` ([git-tool-workflow.md](git-tool-workflow.md)). The 500 MiB mixed-v4 tree **cannot** be the Git working tree.

For `git-tool-{100,500}-mixed-v4` only, when registered:

- File counts still 2,000 / 5,000.
- At most one 50 MiB blob at frozen path `wide/s000-f000.dat`, unchanged by the Git edit schedule.
- Remaining files are 4 KiB: tier 100 is 60,616,704 mixed-tree bytes; tier 500 is 72,904,704. Plus 2,500-byte `tracked/` / `added/` change-schedule files. Working tree ≤ 80 MiB.
- Fixture profile `workspace-mixed-v4-git` so the 500 MiB workspace tree cannot cache-hit.
- `.gitignore` excludes `wide/s000-f000.dat`. Isolation env and `GIT_CONFIG` table unchanged.
- Do not git-add or rewrite the 50 MiB blob.
- Conservative `.git`+tree allocation bound must stay ≤ 256 MiB or the case must not register.

A fixture self-check must prove the 256 MiB bound before these IDs stay registered.
